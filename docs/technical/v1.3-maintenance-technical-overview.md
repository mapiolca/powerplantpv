# Vue technique v1.3 Maintenance

Ce document consolide les notes techniques PR1 à PR11 de PowerPlantPV 1.3 Maintenance.

## Architecture

La maintenance v1.3 repose sur les objets natifs Dolibarr et sur des objets PowerPlantPV spécialisés.

- Centrales : objet `PowerPlant`.
- Contrats et services : objets natifs `Contrat` et lignes de contrat.
- Interventions : objet natif `Fichinter`.
- Rapports : snapshot PowerPlantPV lié à une intervention.
- Relevés : archive PowerPlantPV par centrale.
- PDF : modèle Fichinter `powerplantpvreport`.

Les liens centrale/contrat/intervention utilisent les liens natifs Dolibarr. Le module ne crée pas d'intervention automatiquement. Lorsqu'une intervention de nature maintenance est créée avec une centrale liée, `PowerPlantPVMaintenanceContractLinker` peut ajouter automatiquement le lien natif vers le contrat de maintenance actif si aucun contrat n'est déjà fourni.

## Triggers

Le recalcul maintenance PR11 utilise des triggers core Dolibarr vérifiés en v20 :

- contrats : `CONTRACT_CREATE`, `CONTRACT_MODIFY`, `CONTRACT_VALIDATE`, `CONTRACT_REOPEN`, `CONTRACT_DELETE` ;
- lignes de contrat : `LINECONTRACT_INSERT`, `LINECONTRACT_MODIFY`, `LINECONTRACT_DELETE`, `LINECONTRACT_ACTIVATE`, `LINECONTRACT_CLOSE` ;
- interventions : `FICHINTER_CREATE`, `FICHINTER_MODIFY`, `FICHINTER_VALIDATE`, `FICHINTER_UNVALIDATE`, `FICHINTER_CLOSE`, `FICHINTER_DELETE` ;
- lignes d'intervention : `LINEFICHINTER_CREATE`, `LINEFICHINTER_MODIFY`, `LINEFICHINTER_DELETE` ;
- liens natifs : `OBJECT_LINK_INSERT`, `OBJECT_LINK_MODIFY`, `OBJECT_LINK_DELETE`.

Le trigger `PowerPlantPVMaintenanceTriggers` délègue à `PowerPlantPVMaintenanceRecalculator`. Sur `FICHINTER_CREATE`, il tente d'abord la liaison automatique intervention-contrat de maintenance via `PowerPlantPVMaintenanceContractLinker`, puis lance le recalcul. Le recalcul et la liaison sont non bloquants : une erreur est journalisée, mais l'action Dolibarr source n'est pas annulée.

Les triggers custom historiques PowerPlant/Attestation non-CRUD restent présents pour compatibilité Agenda/Notifications existante. Ils ne sont pas étendus par la v1.3 Maintenance.

## PDF

Le modèle `core/modules/fichinter/doc/pdf_powerplantpvreport.modules.php` génère le PDF depuis l'intervention et le snapshot de rapport.

Le PDF :

- ne crée pas de snapshot ;
- ne recalcule pas le rapport ;
- affiche un état minimal si aucun rapport n'existe ;
- lit les fichiers et images depuis le stockage documentaire PowerPlantPV ;
- utilise `setPageOrientation('', true, $heightforfooter)` et des pieds de page page par page.

## Synchronisation des index

`PowerPlantPVReportBuilder` synchronise les relevés production/consommation après persistance complète du snapshot, uniquement pour les rapports enregistrés.

L'anti-doublon repose sur `PowerPlantPVIndexReading::fetchByReportSource()` et sur la clé source :

- entité ;
- centrale ;
- intervention source ;
- rapport ;
- type de relevé ;
- compteur ;
- équipement de rapport.

Une sauvegarde brouillon ou un recalcul désactive les anciennes lignes provisoires de ce rapport.

## Snapshot rapport

Le premier enregistrement crée un snapshot :

- nature d'intervention ;
- modèle de rapport ;
- centrales ;
- prestations sources ;
- équipements ;
- sections ;
- champs ;
- mesures DC ;
- fichiers.

Le recalcul avant verrouillage reconstruit le snapshot depuis les sources courantes et conserve les valeurs par clé stable. Après signature ou clôture de l'intervention, le rapport devient en lecture seule.

## Calcul des échéances

`PowerPlantPVMaintenanceScheduler` calcule les statuts depuis :

- centrales visibles ;
- contrats liés ;
- services de contrat actifs ;
- prestations de maintenance attachées aux produits/services ;
- période de maintenance du contrat ;
- interventions liées couvrantes ;
- statut clôturé ou signé de l'intervention.

Statuts supportés :

- `not_required`
- `planned`
- `scheduled`
- `due`
- `overdue`
- `covered`
- `incomplete`

Le module ne persiste pas de cache de planning. Les listes et calendriers relisent les sources de planification. Les statistiques pluriannuelles utilisent directement les fiches d'intervention de maintenance datées, dédoublonnées par intervention, avec `dateo` prioritaire et `datec` en dernier recours. Lorsqu'une intervention clôturée ou signée couvre la période courante, le module avance toutefois les extrafields de prochaine période du contrat d'un seul intervalle de récurrence ; ces extrafields restent la source de vérité contractuelle.

`PowerPlantPVMaintenanceStatisticsService` produit les séries mensuelles, les synthèses annuelles et les répartitions comparatives sans table de cache supplémentaire. Son périmètre SQL applique `getEntity()` aux centrales, interventions et natures, ainsi que le tiers de l'utilisateur externe.

Le statut `planned` est soumis au délai `POWERPLANTPV_MAINTENANCE_PLANNING_LEAD_DAYS`, configuré par entité et initialisé à 30 jours. Le statut `scheduled` conserve séparément `scheduled_intervention` et reconnaît une intervention brouillon/validée/facturée en mode `created`, ou validée/facturée en mode `validated`. La nature doit être active et de maintenance, les liens centrale et contrat doivent être présents, les dates valides et la période chevauchée. `covering_intervention` reste prioritaire pour une intervention clôturée ou signée.

## Rappels planifiés

`PowerPlantPVMaintenanceReminder` fournit deux méthodes cron natives :

- `runWeeklyReminder()`
- `runMonthlyReminder()`

Les deux méthodes utilisent `PowerPlantPVMaintenanceScheduler::getMaintenanceRows()` avec les statuts `planned`, `due`, `scheduled` et `overdue`. La fenêtre est calculée depuis l'exécution réelle : aujourd'hui 00:00 à J+6 23:59:59 pour l'hebdomadaire et à J+29 23:59:59 pour le mensuel ; les retards sont ajoutés sans borne d'ancienneté puis dédoublonnés par centrale, contrat et période.

Constantes de configuration :

- `POWERPLANTPV_MAINTENANCE_PLANNING_LEAD_DAYS`
- `POWERPLANTPV_MAINTENANCE_SCHEDULED_INTERVENTION_MODE` (`created` par défaut ou `validated`)
- `POWERPLANTPV_MAINTENANCE_WEEKLY_REMINDER_ENABLE`
- `POWERPLANTPV_MAINTENANCE_WEEKLY_REMINDER_STARTTIME`
- `POWERPLANTPV_MAINTENANCE_MONTHLY_REMINDER_ENABLE`
- `POWERPLANTPV_MAINTENANCE_MONTHLY_REMINDER_STARTTIME`
- `POWERPLANTPV_MAINTENANCE_REMINDER_USER_IDS`
- `POWERPLANTPV_MAINTENANCE_REMINDER_EMAIL_TEMPLATE`

Les envois sont construits par destinataire avec ses droits et `User::$lang`. Ils contiennent des liens absolus vers la centrale, le contrat et l'intervention. Les marqueurs sont conservés destinataire par destinataire : un échec SMTP partiel ne réessaie que les échecs. Les échecs d'écriture du marqueur ou de reprogrammation provoquent un retour cron négatif. Le verrou MySQL inclut l'entité et le rattrapage avance jusqu'à la première occurrence strictement future, sans rafale d'envois.

## Activation et réactivation

L'activation :

- charge les tables SQL ;
- applique les migrations de schéma idempotentes ;
- ajoute les extrafields nécessaires ;
- installe les dictionnaires et modèles par défaut ;
- enregistre le modèle PDF `powerplantpvreport` si absent ;
- conserve les lignes documentaires déjà présentes.

La désactivation ne doit pas effacer les réglages métier, modèles sélectionnés, dictionnaires personnalisés, réglages Multicompany, Agenda, Notifications ou Cron.

## Tests automatisés

La suite `test/PowerPlantPVMaintenanceSchedulerTest.php` couvre les modes `created`/`validated`, la priorité de couverture et les règles de liaison/date/chevauchement. La suite `test/PowerPlantPVMaintenanceReminderTest.php` couvre les bornes J+6/J+29, le rattrapage, les verrous par entité, les marqueurs, le dédoublonnage, les retards historiques, la politique d'échec SMTP/persistance, les traductions FR/EN et les liens absolus. Elle utilise PHPUnit fourni par le Dolibarr parent et n'ajoute aucune dépendance Composer au module.

## Risques connus

- Pas d'instance Dolibarr locale dans ce dépôt pour valider l'activation réelle en base.
- Pas de PHPStan local configuré dans le module.
- Les anciens triggers custom non-CRUD du périmètre PowerPlant/Attestation restent une dette historique à traiter dans une migration dédiée, pas dans PR12.
- La signature en ligne Fichinter de Dolibarr v20 ne fournit pas de trigger Fichinter dédié ; une signature seule peut nécessiter un recalcul manuel ou une autre action source.
- Les personnalisations de modèles doivent préserver les codes techniques utilisés comme clés stables.
